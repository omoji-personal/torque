# /discovery

Carry discovery from stakeholder input to implementable requirements and an agreed next step.

**Interface:** Guided recipe using existing tools. A slash command is an assistant instruction, not a separate shell executable.

Start with the engagement objective, audience, existing process and known constraints.
Read provided requirements, meeting notes and prior decisions. Ask only the questions
that affect the solution; continue artifact organization and investigation independently.

Map current and desired process, users/roles, data/entities, lifecycle/statuses,
exceptions, volumes, integrations, reporting and nonfunctional needs. Investigate
the actual org to distinguish requested change from existing capability. Use meeting
processing or normal document tools for supplied recordings and notes.

Produce a clear problem statement, process map, prioritized requirements/user stories,
acceptance examples, data/permission implications, dependencies, assumptions and
unanswered questions. Identify configurable solutions and custom development only
where justified. Reusable modules and maintainable admin changes matter alongside
bulk behavior, error handling and user experience.

Keep requirements, solution options and accepted decisions distinct. When asked to
implement, turn agreed scope into a task/change plan and proceed through current
metadata, development, validation, execution and verification. Discovery is not a
permanent analysis stop. Save the source-backed requirements and a concise session delta.

If requirements, business rationale or dependency maps already exist in the team's
system of record, retain their identifiers and relevant source references rather
than creating a competing catalogue. An optional Torque change record can connect
the selected outcome, acceptance criteria and decisions to execution evidence and
handoff. Preserve the source's actual status; a linked ticket is context, not proof
of implementation or acceptance.
