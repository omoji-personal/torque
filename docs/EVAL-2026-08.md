# Torque — product and roadmap evaluation · 2026-08-03

**What this is.** An external step-back review of the whole project — what is built, how solid
it is, whether the position is real, and whether the roadmap points at the right things.
Produced by a Claude Code review session on 2026-08-03 at commit `04d142a`, from three passes:
a code-reality survey of `bin/` and `hooks/`, a survey of the validation harness, and web
research on the August-2026 competitive landscape (sources inline).

**How to read the numbers.** This is a dated snapshot. Every count in it was re-derived from
the tree at `04d142a` and will drift as the tree moves; that is expected and fine. This file
is deliberately *not* a surface `claimed_counts` should scan — see the note at the end of
`docs/HANDOFF-DEFECTS-2026-08.md` on living documents versus dated ones.

---

## The verdict in four sentences

This is, at its scale, an unusually rigorously self-validated piece of agent tooling — and the
competitive research confirms the position is real white space: as of August 2026, nothing
open-source or commercial combines deterministic Salesforce-semantic gating, live org
classification at write time, operator-minted approval, and a self-proving harness inside a
third-party agent's tool loop. The strategic problem is not the mechanism and not the
position; it is that the project has extraordinary *internal* epistemics and zero *external*
epistemics — no users, no issues, an empty lesson queue, and a roadmap whose every item is
more engineering. Meanwhile the ground is moving in a direction that erodes the *safety* half
of the thesis (agent runtimes and generic firewalls are absorbing generic gating) and inflates
the *verification* half — which is where roadmap steps 3–4 already point, so the direction is
right but the sequencing buries the two highest-leverage moves: contact with users, and the
PATH shim. Held to its own honesty standard, the repo is also developing exactly the drift its
thesis predicts — a stale count in the one file the count-checker does not scan, a check that
cannot fail, a dead safety guard — none fatal, all catalogued in the handoff document.

## 1. The state, measured

The enforcement layer — `shellparse.py` (1,329 lines), `lib.py` (1,060), two gates, 193
on-disk + 3 minted fixtures, 15 mutators, 128 differential-fuzz cases, zero third-party
dependencies in the security path — is the mature part: fail-closed by construction (a
crashing, timing-out, or import-broken gate denies), adversarially exercised, honest about its
boundary.

The operations layer the README leads with is real but materially narrower than the prose:

- `torque-blast-radius` queries 7 automation surfaces of the ~15 that exist (it has no
  duplicate rules — which the catalogue itself carries an entry for — no assignment or
  escalation rules, sharing recalculation, invocable Apex, or platform-event subscribers).
  Its honesty machinery (UNDETERMINED / exit 3) is the best-defended claim in the repo, with
  four independent mechanisms. Side effect nobody states: because every roll-up candidate is
  unconditionally suffixed UNDETERMINED, any object whose parents carry a roll-up summary
  field can never exit 0 — exit 3 is the *normal* case on a real org.
- `torque-checkup` runs ~12 probes hardcoded to specific objects (`Account`,
  `Account.My_Field__c`); it is not org-adaptive.
- `torque-shadow` is a wrapper around one Apex template; there is no path from an actual
  `sf data update` command, and its protected-object refusal is dead code (handoff item A1).
- The lesson observer has never captured an organic lesson: `local/lessons/candidates.jsonl`
  does not exist, and the anti-rot check passes vacuously on absence. The README's sample is a
  deliberately-run probe.

Corrections to published numbers, verified against artifacts:

| Claim | Reality |
|---|---|
| "66 checks" (ROADMAP.md) | 71 (50 static / 68 capability / 71 release). 66 matches an attestation five commits stale — and `claimed_counts` does not scan ROADMAP.md, which is precisely why the one wrong count lives there |
| VALIDATION.md latest entry: "59/59 checks, 11 mutators" | The newest attestation records 71/71 and 15; the run after P7 was never logged |
| "retrieval 94% recall / 85% precision" | 94% is *matched* recall; *surfaced* recall — what an operator actually sees after the 2-slot display limit — is 86.4%, and only matched has a floor. Precision is 85.3% against a FAIL floor of 85.0%: one more false positive fails the build |
| 196 fixtures, 15 mutators | Both check out exactly |

Fresh-user experience notes: a release run takes ~3.5–5 minutes and leaves a `_del` field
tombstone on `Account` per run; `browser_render` looks for Chromium only at a macOS path, so
on Linux/Windows the release verdict is unreachable-PASS even with Playwright installed;
`--profile capability` without `--target-org` fails with a TypeError-shaped FAIL rather than a
SKIP; and `impact_bound_approval` reddens on any org with zero Leads.

Validation asymmetry worth holding in mind: of the 71 checks, ~28% validate Torque's own
consistency (counts, docs, labels, hygiene), ~51% validate the refusal machinery, and exactly
4 exercise a real Salesforce operation end to end (`probe_cycle`, `mass_update_cycle`,
`impact_bound_approval`, `browser_render`). The harness is world-class at proving the gate;
as the roadmap builds the operations side, the harness has to grow in the same direction.

## 2. What is genuinely unusual

Four things here are rare, and they compound:

1. **Enforcement labeling that is itself checked** — hook-enforced / harness-enforced /
   model-honored, with mutators proving guards are load-bearing. The differential fuzzer is
   the standout: it establishes ground truth by executing generated commands against real bash
   with a recording `sf` stub and a canary secret — the only part of the suite not testing a
   shape someone already imagined.
2. **Authorization by identity, not inference** — live `IsSandbox` at write time. The
   Salesforce DX MCP server, by comparison, ships only a *static* org allowlist with no notion
   of what is production.
3. **Knowledge that argues with itself** — the `deleted-field-rename` entry documenting its
   own former folklore; the profile-deploy entry corrected by experiment that now runs on
   every release. No vendor doc and no model does this.
4. **A validation log that documents its own past false claim** (P5's phantom attestation,
   corrected in P6).

The demo is the best three seconds of first-touch UX in the repo, and `DESCRIBING-TORQUE.md` —
copy under version control with drift checks — is a discipline most funded startups lack.

## 3. Three structural findings

### Finding 1 — supply without demand signal

Fourteen adversarial rounds, ~55 findings fixed, three audit lenses — every one author-run,
model-executed. The repo went public 2026-07-31: zero stars, forks, issues. The lesson
observer — the feature whose premise is "the tool learns from real use" — has never fired
organically. `/status`, the newest commit, reads two files under gitignored `local/` and is
unusable by anyone but the author. This is a project that has been *proven* intensively and
*used* barely, and all four roadmap items extend the proving. The most informative next unit
of work is not code: it is five real Salesforce practitioners running `torque init` against
their own dev orgs while someone watches where they stumble.

One phrase to fix before a skeptical visitor finds it: ROADMAP.md calls the fixture corpus
"a year of adversarial rounds" over a git history spanning three days. The rounds were real;
the phrasing will read as inflation to exactly the audience the project is built to convince.

### Finding 2 — the moat is migrating from where it was built to where the roadmap points

The 2026 landscape moved. Claude Code's native permission engine now does operator-aware,
wrapper-aware, substitution-aware shell parsing itself; its sandbox runtime is growing to
cover hooks and MCP servers. Zenity shipped "Runtime Boundaries" spanning Claude Code, Cursor,
and Agentforce in July 2026. MCP policy gateways are a product category. Generic "parse the
shell, block the dangerous thing" is being commoditized by the runtime vendors — that half of
Torque erodes on someone else's schedule.

What nothing else has, confirmed by targeted search: live production classification at write
time, destructive-op approval bound to verified impact, Salesforce-semantic judgment (that a
successful API call can still be a wrong outcome), and in-org verification of done.

Meanwhile the tailwind is enormous and immediate: Salesforce made Claude Sonnet 4.5 the
default coding model in Agentforce Vibes, free in every Developer Edition (April 2026), GA'd
hosted MCP servers, and absorbed the community Claude Code skills library into an official
channel (`forcedotcom/afv-library`). The population of "agents operating on Salesforce orgs"
is exploding right now, the vendor's own tooling ships capability with no judgment layer, and
the guide's honest concession — "Works outside Claude Code: no" — is a smaller liability than
it looks given Salesforce itself just standardized on Claude. The window is open, and it is
now.

### Finding 3 — the drift the thesis predicts is already visible at the edges

Every item below is the "green but wrong" class the catalogue exists to catch, found in a repo
four days old. The full punch list with locations and required proofs is
`docs/HANDOFF-DEFECTS-2026-08.md`; the headline instances:

- `bin/torque-shadow:94` guards protected objects via `hasattr(lib, "protected_object_hits")`
  — a function that exists nowhere, so the refusal promised in the comment ten lines above is
  permanently unreachable. The commit history's own worst-defect pattern ("I listed the risk
  in the docstring and then did not gate on it"), recurring, uncaught.
- `image_manifest` is a catastrophe-class check that cannot fail (manifest absent, zero images
  in `guide/`, passes on an empty loop) — the sin the mutation-testing edifice exists to
  prevent.
- `public_description_accurate` derives mutators=0 and fuzz=0 from expressions that match
  nothing, so it would accept a public description saying "0" and reject the correct "15".
- `TOOLCHAIN.md` says `cli-write-surface.json` is committed and drift-checked at preflight;
  the file does not exist and there is no preflight stage.
- No CI. A GitHub Action running `--profile static` on push is thirty minutes of work and
  would have caught the ROADMAP drift the day it happened.
- Confirmed live while producing this review: a static run in the review container (repo
  outside `$HOME`) turns the whole verdict red on a false FAIL from
  `guards_share_no_blind_assumption` — the assumption-sweep check itself assumes the repo
  lives under `$HOME` (handoff item C9). The other 70 checks pass on a fresh Linux clone.

None of this is fabrication — the code survey's bottom line was "nothing here is a stub or a
mock." It is what three days of solo intensity at this standard leaves at the edges, and the
standard only holds from here with CI and with the checks pointed at the remaining surfaces.

## 4. Competitive landscape, August 2026 (sourced)

**Salesforce's own story.** The DX MCP server (launched June 2025) ships 60+ tools with
*static* org allowlisting (`--orgs`), toolset segmentation, and token hygiene — no read-only
mode, no destructive-op confirmation, no live sandbox-vs-production classification, no
operator-present approval. Hosted MCP servers GA'd April 29, 2026 (Enterprise+, `mcp_api`
scope, permission-model governance). Agentforce Vibes (Oct 2025, built on Cline) became free
in every Developer Edition with Claude Sonnet 4.5 as the default model (April 15, 2026); its
safety stance is human-in-the-loop convention, not a deterministic gate. Salesforce absorbed
the community skills library into `forcedotcom/afv-library`.

**DevOps platforms** converged on "agents inside our governed platform" — the architectural

**Open source.** sfdx-hardis (v7) has a beta agent auto-fix for deploy errors; its safety
model is the CI pipeline, complementary not competitive. The closest neighbor,
`agentgill/sf-skills-public` (21 skills, 14 hooks), states its hooks are "advisory feedback —
they inform but don't block." No project found combines Torque's elements.

**Generic agent-safety layers** are now mainstream — Lasso's MCP gateway (+ Portkey
partnership, Feb 2026), MintMCP, Zenity ("Company to Beat" in a 2026 Gartner report; Runtime

**Claude Code native evolution.** Permission rules are now shell-operator-aware with wrapper

## 5. The roadmap, item by item

**Dropped section — agree, and it is the best part of the document.** Both kills (per-org
compounding profile, catalogue entry-count racing) were correct; the contradiction argument
(knowledge cannot both compound durably and clear on sandbox refresh) is sound. Keep the
narrow survivors: org-Id-keyed findings with freshness, and the lesson pairing.

**#1 Completeness closure — yes, as scoped.** Cheap, uses existing data, directly attacks
failure #2 (incomplete intent). With 39 entries it initially closes over a handful of
operation classes; it is a feature, not a differentiator. Half a step, correctly priced.

**#2 Shadow execution — real and genuinely novel; scope the claim before building the honesty
layer.** Three additions to the planned test-what-does-not-roll-back program:

- *Savepoint rollback does not abort the transaction.* Emails queued via
  `Messaging.sendEmail` before the rollback still send when the anonymous-Apex transaction
  commits; immediate-publish platform events leak (publish-after-commit ones do not). "Residue
  zero" needs per-side-channel qualification, established by test as planned.
- *Shadow DML holds row locks until transaction end* — on a contended sandbox this can collide
  with real users.
- Most important: *a shadow run validates row-level semantics only.* The per-transaction
  governor ceiling means it can never rehearse bulk-job dynamics — chunking, lock ordering,
  partial batch failure — precisely the failure modes the catalogue's own
  `bulk-partial-failure` entry warns about. Shadow + blast-radius together are honest; shadow
  alone, oversold, becomes the kind of claim the rest of the repo refuses to make.

Also: fix the dead protected-object guard (handoff A1) before this ships anything further.

**#3 Completion gate — this is the product, and the deferred "product decision" is ready to be
made now, in favor of verification-led positioning.** Three reasons: the erosion vector
(native runtime policy) attacks the safety half, not the verification half; "the agent said
done and it wasn't" is a scar every agent user has, making demand constant rather than
fear-driven and episodic; and it is the only frame in which "gets better with use" survives
the project's own adversarial review. Design notes: build it as a **tiered ledger**, not a
browser gate with cheap checks attached — SOQL + FieldPermissions + layout membership +
flow-activation catch most of the "deployed but invisible" class in seconds; the non-admin
browser render is the expensive top tier, opt-in per operation. The three gating questions
(non-admin render, wall-clock, flakiness) are right; add a fourth — **false-positive rate** —
because a gate that says not-done when it is done gets routed around exactly as fast as a slow
one. And the non-admin profile needs a spare license and a persona choice per org: per-client
setup friction to price in early.

**#4 Proof-carrying operations — right unifying frame; make it a schema, not a framework.**
The receipt (preconditions, predicted impact, authorization bound to impact, postconditions,
unknowns, evidence) is the artifact a team lead, an auditor, or a future Salesforce-native
gate could consume. Publish it as a versioned JSON schema with a validator, and it becomes the
piece of Torque that outlives any particular enforcement point. "Mostly integration" is
famous-last-words territory; the schema-first version keeps it honest.

## 6. What the roadmap is missing, in the order it should be added

1. **A contact-with-reality milestone.** Ship to five named practitioners; instrument nothing
   new — the lesson queue and the gap-log *are* the instruments; success = one organic lesson
   captured and one stranger's bypass report. The launch is an experiment with a measurement,
   not a marketing event.
2. **The PATH shim, promoted from v2 to next.** Currently framed as security debt; actually
   the highest-leverage architectural move on the board. At exec time there is no expansion
   problem — the shim sees post-expansion argv, which retires the attack class that consumed
   audit rounds 10–16 and most of `shellparse.py`'s 1,329 lines. It closes the disclosed
   subprocess hole, and it decouples enforcement from Claude Code: any runtime that execs `sf`
   — Vibes' Cline, Cursor, a bash script — gets gated. Paired with the hooks (which still
   cover MCP and pre-execution denial), the "Works outside Claude Code: no" row flips. Days of
   work, not weeks, and much of the fixture corpus ports directly.
3. **CI.** Static profile on every push, immediately. Scheduled capability runs against a
   dedicated DE org via JWT auth when feasible.
4. **Distribution as a Claude Code plugin** (plugins bundle hooks + skills + commands), with
   `afv-library`'s Agent Skills compatibility as a second channel. "git clone + init" selects
   for the already-convinced.
5. **Second-operator approval** (remote-signed tokens for approver ≠ operator machine) — the
   first thing a two-person shop asks for; fine post-traction, wrong to leave unmapped.

## 7. Recommended order

1. **Close the credibility gaps** — the punch list in `docs/HANDOFF-DEFECTS-2026-08.md`
   (one to two days), each fix with its fixture, per the repo's own rule.
2. **CI static profile**, same week.
3. **Roadmap #1** (small) **and the launch experiment**, in parallel. Let the gap-log and
   lesson queue decide whether the catalogue grows next or the completion gate does.
4. **The shim**, before shadow — it upgrades the security claim and the addressable market at
   once.
5. **The completion gate** (ledger-first), shaped by what the five users actually got burned
   by, with the receipt schema emerging from it rather than being designed in the abstract.
6. **Shadow's honesty program last** — most novel, least demanded; the correct order to
   resolve in.

One-sentence version: the engineering has earned the right to meet users, the market timing is
unusually good, the roadmap's direction — from "operations layer" to "the thing that will not
let an agent claim done" — is correct, and the two cheapest, highest-leverage moves on the
board, a launch experiment and the exec-time shim, are the two things not yet on it.
