## The boundary

`prod_write_gate.handle_edit` denies any Edit/Write whose payload names a protected path, and
there is no token, flag, or approval that lifts it — unlike a production write, which Layer 3
can authorize, a protected-file edit has no agent-reachable path at all. That is deliberate:
the gate's own source is exactly what an agent must not be able to rewrite.

The predicate is `is_protected_target(path) OR basename in PROTECTED_BASENAMES OR anchor_ref(…)`,
which covers `hooks/`, `bin/`, `.claude/`, `harness/checks/`, `knowledge/`, `local/orgs/`, and —
by basename, wherever it lives — `validate.py`, `lib.py`, `shellparse.py`, `prod_write_gate.py`,
`destructive_data_gate.py`, `torque-approve`, `torque-frontdoor`, `torque-install-gates`,
`settings.json`, `writable-orgs.json`, `protected-objects`, `clean-ip.rules`,
`cli-write-surface.json`, `salesforce-platform.yml`, and the cache/audit files.

## A1, reproduced — and the check that was supposed to catch it

A1 is the flagged priority, so it was reproduced before being handed back.

**The guard is dead, as described.** `lib.protected_object_hits` exists nowhere, so the `hasattr`
at `bin/torque-shadow:94` is permanently False. With classification mocked to a verified developer
org and the subprocess stubbed, `--apex 'delete [SELECT Id FROM Account];'` — an unscoped delete
of a protected object — returns 0 and reaches `sf apex run`.

**The more serious finding is why nobody noticed.** `shadow_cannot_escape_the_transaction` is
catastrophe-class, and it cannot fail. It runs torque-shadow with `--target-org torque-not-an-org`
and asserts the output contains `REFUSED`. But an unresolvable org classifies `production`
(`classify_live`: `_org_display` returns `(None, None)` → `"production"`), which refuses every
body on its own, before either guard is consulted.

> **Correction, same day.** The first falsification written here was invalid, and the method is
> worth recording because it is a trap this codebase sets. It claimed the guard had been
> neutered by setting `ESCAPES = {}` on the imported module. That does nothing: `ESCAPES` is a
> **local inside `main()`**, rebuilt on every call, so the "neutered" run was still fully
> guarded and the evidence proved nothing. Assigning to a module attribute is not neutering a
> function-local. The conclusion survived; the proof did not, and an invalid proof of a true
> claim is the same defect as the check it was written to expose.

Falsified properly, by cutting the escape guard **out of the source** and running three trees:

| tree | old check | new check |
|---|---|---|
| repo, A1 unfixed | **PASS** | FAIL — names the missing protected-object refusal |
| staged, A1 fixed | PASS | PASS |
| staged, escape guard cut from source | **PASS** | FAIL — names the missing escape refusal |

The old check passes in every tree, including one where the guard is physically absent.

So the check has never tested what it claims. It has been asserting that a nonexistent org name
is rejected. That is a B1-class defect — a check that cannot fail — sitting inside group A, and
it is the mechanism by which A1 survived. `image_manifest` is not the only one.

### The fix — written, verified by execution, waiting on one operator command

`local/patches/a1-protected-object-guard.patch` (gitignored; operator-local). Apply with:

```
git apply local/patches/a1-protected-object-guard.patch
```

It was verified by RUNNING the staged copies, not by reading them. Against a mocked developer
org with the subprocess stubbed:

| body | repo today | patched |
|---|---|---|
| `delete [SELECT Id FROM Account];` | rc 0, `sf apex run` invoked | rc 2, refused, no org contacted |
| `delete [select id from account];` | rc 0, invoked | rc 2, refused (case-insensitive) |
| `update [SELECT Id FROM Contact];` | rc 0, invoked | rc 2, refused |
| `insert new Lead(LastName="x");` | rc 0, invoked | rc 0, still runs |

The last row is the control: without it the other three prove only that something refuses
everything.

Sharing one matcher matters here because `no_divergent_twins` exists for exactly this pair, and
`_shield_text`'s docstring already records that this floor was fixed on the CLI path and missed
on the Apex path once before.

1. **`hooks/lib.py`**, beside `protected_objects()` — add the matcher, and only the matcher:
   `protected_object_hits(text) -> list`, returning `[obj for obj in sorted(protected_objects())
   if re.search(rf"\b{re.escape(obj)}\b", text or "", re.IGNORECASE)]`. Case-insensitive and
   word-bounded, matching `_shield_text`'s semantics, because Apex sObject names are
   case-insensitive and that equivalence has now been fixed three times in three near-identical
   guards.
2. **`hooks/destructive_data_gate.py`** — `_shield_text` calls it and denies on a hit. Policy
   stays at the call site: a hook must exit non-zero, a CLI has a return code to give.
3. **`bin/torque-shadow:94`** — drop the `hasattr` and call it directly. The name the dead code
   already used is the name to implement, so the call site needs no other change.

Checked against the existing suite: `shield_is_case_insensitive` exercises one object per case,
so a sorted return cannot change which object a message names, and its negative case
(`Widget__c`) still yields an empty list.

**The proof must fix the check, not extend it.** Adding a protected-object arm to
`shadow_cannot_escape_the_transaction` while it still runs against `torque-not-an-org` would add
a second assertion that passes for the same wrong reason. The check has to distinguish the
refusal REASON — assert the escape shapes produce "can leave the transaction" and the protected
object produces "protected object", not merely that the word REFUSED appears. Then neutering
either guard turns the message into "classified 'production'" and the check goes red, which is
the falsification the handoff asks for and the property the check has never had.

## So this does not happen again

Two separate fixes, because there are two separate problems.

**Knowing the boundary** — `scripts/write-surface.py`, which asks `lib` and `shellparse` the same
question `prod_write_gate` asks, rather than restating their rules where the copy could drift:

```
python3 scripts/write-surface.py --plan docs/HANDOFF-DEFECTS-2026-08.md
```

Run against the handoff that produced this document, it reports 14 blocked paths in about a
second. That is the finding this file spent half a context window establishing by being refused
one edit at a time. It is referenced from CLAUDE.md so a session meets it before planning, and
the `--plan` mode belongs to whoever WRITES the next punch list as much as to whoever works it: a
list assembled from a code survey will name files the agent cannot touch, because a code survey
does not ask that question.

**Crossing it** — `docs/MAINTAINER-MODE.md`. Discoverability alone would only mean failing faster.

Neither changes the boundary, and neither should. The gate refusing to let an agent rewrite the
gate is the property the whole project rests on; what was missing was a way to see it coming.
